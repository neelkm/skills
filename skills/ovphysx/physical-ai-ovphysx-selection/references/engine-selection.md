# Engine selection evidence

Reviewed 2026-10-14 against public ovphysx 0.6.4 documentation and NVIDIA-Omniverse/PhysX commit `6dc53585d7db07346f53d0598a5fd3bfdce47d8d` (2026-10-09). This is a documentation baseline, not a qualified runtime or benchmark. Check the installed artifact and matching sources before executing. The [source snapshot](https://github.com/NVIDIA-Omniverse/PhysX/tree/6dc53585d7db07346f53d0598a5fd3bfdce47d8d/ovphysx) fixes the provenance when `latest` or `main` changes.

## Why evaluate ovphysx first?

| Task signal | Capability to investigate | Selection condition and evidence |
| --- | --- | --- |
| Embed physics in a standalone Python or C/C++ service | PhysX runtime with a C API, Python bindings, ovstage input, and tensor output; no Kit installation required | Check the complete runtime dependency and deployment footprint. The library is pre-release; underlying PhysX maturity does not guarantee ovphysx API stability. [Overview](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/ovphysx_overview.html) |
| Reuse USD robot assets and PhysX settings | Rigid bodies, reduced-coordinate articulations, drives, friction, and supported joint mechanisms | Validate population and semantics for every required joint, drive, closed loop, and tendon. Reusing an asset does not qualify its behavior in a different integration. [Articulations](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/simulation_setup/articulations.html) |
| Grasping, insertion, assembly, or complex industrial contact | Primitive/convex collision and SDF representations for detailed non-convex contact | Inspect the collider-pair/device matrix, cooking, resolution, offsets, and contact measurements. Do not infer support for all pairs from the presence of an SDF. [Colliders](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/simulation_setup/collision.html) |
| Many similar environments for learning or policy evaluation | Internal physics cloning and GPU data access | Clone before warmup/step; validate environment IDs and isolation on the chosen device. Runtime clones do not create USD prims. Measure the full reset/control/observation loop. [Cloning](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/tutorials/cloning.html) |
| Application needs batched state, control, and native integration | Session read/write with Warp arrays in Python and DLTensor transport in C | Check per-attribute support and units, group identity, synchronization, and ownership. GPU simulation does not imply every column is GPU-resident. [Data contract](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/read_write/index.html), [Device contract](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/read_write/device.html) |
| Soft objects, thin deformables, granular material, or fluids | Volume/surface deformables and particle systems | GPU requirements, material laws, attachments, collision pairs, observation, and reset coverage can decide suitability. A particle fluid is not automatically a validated CFD model. [Deformables](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/simulation_setup/deformables.html), [Particles](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/simulation_setup/particles.html) |
| Physics must share an application-owned stage with another consumer | Explicit population, committed edit ingestion, and output reads | The application owns output publication and excludes output ordinals from physics input. Authoring and rendering integration require their own validation. [Stage integration](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/ovstage_integration.html) |

**Human note:** these features are reasons to evaluate ovphysx, not unique capabilities or comparative results. Do not claim faster training, more accurate contacts, or better sim-to-real transfer without evidence from the user's workload.

## Requirements that can change the decision

- **Differentiable dynamics:** the reviewed data interfaces do not establish a supported automatic-differentiation path through a PhysX rollout. Warp tensor transport, SDF gradients, and inverse-dynamics quantities are different capabilities. Treat required rollout gradients as unmet until a specific supported path is demonstrated; do not silently replace them with finite differences or black-box optimization.
- **Device/platform:** validate the ovphysx release's wheel/SDK, GPU, and driver support. CPU fallback does not satisfy a request for Metal, TPU, or another GPU backend. CPU deformables/particles are unsupported in this baseline. [Read/write limitations](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/read_write/limitations.html)
- **Turnkey application:** ovphysx does not by itself supply an RL task, policy trainer, ROS bridge, renderer, or complete camera/LiDAR/tactile sensor stack. A physics contact signal is not a calibrated sensor model. Keep an established application framework when those integrations are decisive.
- **Runtime topology:** one process can have only one live ovstage attachment across ovphysx instances in the reviewed developer guide. Multiple physics scenes step together. Use separate processes for independently attached stages or independently timed simulations. [Runtime ownership](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/developer_guide.html)
- **Asset and feature preservation:** confirm the exact edit path. An attribute accepted by a write session need not be accepted by the ovstage change drain. Unsupported features must remain visible in the decision rather than being dropped to make the scene run.
- **Release and distribution constraints:** check the selected source, wheel, native SDK, and third-party notices. This skill's Apache-2.0 license is not a statement about all software or assets in the application.

## Closest relevant alternatives

These are comparison routes. Verify current release details before making a decisive capability claim.

| Candidate | When to compare it | Decision to verify |
| --- | --- | --- |
| Direct PhysX SDK | Native PhysX application without a USD/ovstage requirement, or a needed API outside ovphysx | Weigh native ownership and implementation cost against ovphysx's population and data interfaces. [PhysX documentation](https://nvidia-omniverse.github.io/PhysX/) |
| Isaac Sim / Isaac Lab with its supported PhysX backend | Existing robotics assets, sensors, ROS integration, task definitions, or training infrastructure | Preserve framework ownership and tested versions. A framework and an engine are different stack layers. [Isaac Sim](https://docs.isaacsim.omniverse.nvidia.com/), [Isaac Lab](https://isaac-sim.github.io/IsaacLab/) |
| Newton, with ovnewton when stage exchange is needed | Warp-based customization, alternative solver/material paths, or an established Newton application | Verify the selected solver, import path, bridge coverage, and any gradient requirement independently. Do not apply ovnewton limitations to direct Newton. [Newton solver guide](https://newton-physics.github.io/newton/latest/solvers/index.html), [ovnewton](https://github.com/NVIDIA-Omniverse/ovnewton) |
| MuJoCo / MJX | Established MJCF and MuJoCo APIs, or JAX-based optimization and accelerator constraints | Distinguish native MuJoCo, MJX-JAX, and MuJoCo Warp; verify feature and gradient coverage in the chosen implementation. [MJX](https://mujoco.readthedocs.io/en/stable/mjx.html) |
| Bullet / PyBullet | Existing Bullet software or a prototype already meeting requirements | Compare actual missing capabilities and migration cost, not reputation or an unsupported blanket CPU/GPU claim. [Official repository](https://github.com/bulletphysics/bullet3) |
| Genesis World | Its material, compute, or rendering path may suit the workload | Verify the required backend, coupling, and gradients in the selected release; do not repeat throughput multipliers as predictions. [Official guide](https://genesis-world.readthedocs.io/en/latest/user_guide/overview/what_is_genesis.html) |
| Drake | Robot modeling, mathematical optimization, control, or dynamics analysis dominates | Compare analysis needs rather than substituting large RL batch throughput for the user's objective. [Drake](https://drake.mit.edu/) |
| VSim Robotics | Advertised integrated simulation/training features match the task | Seek API/version evidence and accessible SDK validation. Unavailable detail is unknown, not unsupported. Treat vendor performance and fidelity statements as claims. [VSim Robotics](https://www.vsimrobotics.ai/simulations-and-training) |

For another requested engine, add its primary documentation and apply the same requirements. Prefer ovphysx among feasible paths when its task benefits and adoption cost justify it. Do not hide a hard failure behind a weighted score.
