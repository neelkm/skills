# Execute a representative ovphysx workflow

Use the sections needed for the task. Baseline: ovphysx 0.6.4, reviewed 2026-10-14. For signatures and supported attributes, consult the selected release's documentation and packaged examples. The procedures below are task guidance, not measured results.

## Prepare the asset and the stage

Confirm units, up axis, gravity, collision geometry, masses/inertia, articulation roots, joint axes/limits, drives, and material bindings. Check how closed loops are represented; an articulation tree and its loop-closing constraints are different parts of the model. Preserve physical requirements during conversion from URDF, MJCF, or CAD. A visual mesh is not sufficient collision or robot-dynamics data. [Articulations](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/simulation_setup/articulations.html)

Register all required codeless schemas before first population. Populate an explicit physics-inclusive domain, seal its ordinal, then attach. For arbitrary USD, use `PopulationDomain.ALL`: the reviewed physics-only population path can omit collider bindings under native scene-graph instances. Physics-only is suitable when that topology is known absent. Reuse application-owned stages; do not silently repopulate an existing renderer's stage. [Population and schema ordering](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/ovstage_integration.html)

## Control, observe, and reset a robot

Use the session read/write API for new supported operations. Read actual joint state, compute controls, open a write session for the required target or effort attribute, fill every mapped element, commit, step, and read the resulting state. Verify the relevant drive is enabled and that targets are not mistaken for measured joint positions. Inputs such as drive targets persist until changed; write-only controls such as force/wrench are consumed and cleared each step. Session writes update simulation state, not the source USD. Confirm each attribute's write support and persistence in the [write contract](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/read_write/writable.html).

Map values through each group's own prim identities. A query can succeed with no matching data, and attributes may omit inapplicable objects. Do not assume that group order or row count stays constant across attributes, heterogeneous articulations, or topology changes. Handle fixed and per-object array groups explicitly.

The session API uses **mixed angular units**. Rotational joint positions/targets use degrees and joint velocities use degrees/s. Rigid-body/link angular velocity uses rad/s. Whole-articulation inverse-dynamics angular coordinates use radians. Positions use scene length units; quaternions use `xyzw`. Frames are attribute-specific. Convert at a deliberate controller boundary, not by applying one angular conversion to all tensors. [Data model](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/read_write/data_model.html)

Check each tensor's device, even in a GPU scene. Read buffers belong to their session; copy data that must outlive it. Mapped write buffers become invalid after commit/release. When using external CUDA streams, wait for read readiness and supply completion synchronization for writes. Release sessions after use to permit buffer reuse. DLPack transport alone does not establish zero-copy behavior for the entire application. [Device and lifetime contract](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/read_write/device.html)

For an episode reset, restore the selected environments' root pose/velocity, joint position/velocity, controls, and task state through supported writes; reset observations and controller state consistently. Do not teleport individual articulation links as a substitute for joint/root reset. Verify the next step and ensure unselected environments are unchanged. Distinguish state reset from `reset_stage()`, which changes the stage lifecycle and requires recreating affected bindings/resources. Do not promise exact replay without qualifying solver state, seeds, hardware, and determinism limits. [Articulations](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/simulation_setup/articulations.html), [Ownership and lifecycle](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/developer_guide.html)

## Batched learning and policy evaluation

Create all direct physics clones before warmup or the first step. A DirectGPU read can be empty before the first step, and its write commit is refused until initialization has occurred. Finish cloning, perform the required initial step, then establish/reset the episode's intended initial state and time accounting. Do not count an initialization step as an unrecorded training transition. [Cloning](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/tutorials/cloning.html), [First-step rules](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/read_write/data_model.html)

When several clone calls build one logical environment, assign consistent `env_ids` across its components. ID-based collision isolation requires GPU dynamics and GPU broadphase. CPU clones need disjoint anchor transforms or another verified isolation arrangement. Test that objects in one environment cannot disturb another. Internal clones create physics objects, not USD prims; check identity and observation coverage through the selected API instead of assuming every clone has a populated stage prim. A renderer needs a deliberate representation and mapping. [Clone semantics](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/tutorials/cloning.html)

Measure setup/cooking and steady-state execution separately. Include controls, observations, resets, policy inference, transfers, and publication when those are in scope. Verify GPU buffer capacity under the actual contact load. Use one shared infinite ground plane or separate finite grounds; duplicating infinite planes creates overlapping collision geometry. Multiple scenes in one stage step together; independently attached stages or clocks need the process isolation described in the developer guide. [Performance guide](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/guides/performance.html), [Runtime model](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/developer_guide.html)

## Contact-rich manipulation and industrial motion

Start with collision geometry that preserves the required physical features. Compare primitives, convex decomposition, and SDF where supported. Check actual contact pairs, cooking diagnostics, resolution, contact/rest offsets, self-collision, friction, mass ratios, timestep, and actuator limits. A rendered part that looks correct can still have an unsuitable collision approximation. Confirm contact-force units, timestep conversion, aggregation, and buffer completeness in the selected contact API. [Collision guide](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/guides/collision_tuning.html), [Contact bindings](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/tutorials/contact_binding.html)

Use TGS as the documented default when appropriate; compare PGS only as a controlled change against the same physical targets. Tune timestep, iterations, contacts, and gains in bounded experiments. Avoid compensating for a bad asset with extreme friction or gains. Stabilization adds damping and can change precise robot/industrial interactions; do not enable it merely to hide instability. Record tradeoffs in slip, penetration, tracking, force, and runtime. [Scene settings](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/simulation_setup/physics_scene.html), [Robot stability](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/guides/articulation_stability.html)

For conveyors and moving supports, distinguish authored transforms, kinematic motion, and surface velocity. Check the interaction mode that actually transfers motion to the rider; do not infer physical support motion from visual movement. Use the release's [kinematic-support example](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/simulation_setup/kinematic_support.html).

## Deformables and particles

Confirm GPU availability, material law, simulation mesh, rest topology, collision pairs, attachments, and state/reset access before recommending the path. The baseline supports volume and surface deformables but documents important limitations: CPU simulation is unavailable, static friction is unsupported, and surface deformables use the simulation mesh for collision. Do not carry old particle-cloth assumptions into the surface-deformable path. Test the required attachment/contact behavior and calibrate against reference material measurements. [Deformables](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/simulation_setup/deformables.html)

For particle work, specify the intended material and observable rather than treating all particle models as interchangeable. Verify neighbor/buffer limits, contact support, resolution sensitivity, and read/write device placement; the reviewed session contract stages particle position/velocity writes on CPU. [Particles](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/simulation_setup/particles.html), [Device contract](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/read_write/device.html)

## Shared-stage and rendering handoff

The application reads physics output and publishes it to ovstage. Choose distinct ordinals for application edits and simulation output. For example, after initial attach at 1, drain control ordinal 2, publish output at 3, and drain the next control at 4. Call `update_from_ovstage(4, 4)`, not a range that includes output ordinal 3. Seal writes before consumers read them.

Use the matching output-copy utility when its contract fits. Its world-matrix publication is not a general authoring of local transforms or propagation to descendants. Fixed pose publication requires position and orientation together. Update hierarchy-dependent state and the renderer in the documented order; preserve any application-owned cache's refresh/lifetime rules. Rendering and sensor validation remain separate from physics validation. [Integration and output helper](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/ovstage_integration.html)

Session writability is not a guarantee of incremental stage-edit coverage. For live changes, check whether the exact field is applied by the drain, requires reparsing, or is unsupported on the selected mode. Do not silently change a live-edit requirement into stop/reload. [API gaps](https://nvidia-omniverse.github.io/PhysX/ovphysx/0.6.4/read_write/limitations.html)
